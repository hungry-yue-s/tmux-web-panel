tmux-web-panel · 插件架构

整个面板现在由插件组装

参照 DeepSeek Harness 的做法，面板改跑在 Cordis 插件内核上。原来一个入口文件里的手工接线，拆成了 42 个各自声明依赖的插件；原来手写的主页面，改由各插件声明的脚本组装。业务代码原样保留。

24插件，列在 profiles/panel.yml
691 → 5行：server/index.js 只剩兼容入口
~350行内核：kernel/ 三个文件，只做组装
~2500个测试，无新增失败

0:改了什么

同一件事，前后对比：把“置顶窗口”功能接到服务器上。

以前 · server/index.js691 行手工接线
296 const pinStore = new PinStore(
297   join(configDir, 'pins.json'));
    …
352 app.use('/api/sessions', sessionsRouter);
353 app.use('/api/sessions/:name/windows', …);
    … 三十多行 app.use …
365 app.use('/api/pins', createPinsRouter(pinStore));
366 app.use('/api/share', createShareRouter(shareStore));
    … 关机时手工逐个 stop …
  • 所有模块在一个文件里 new 出来，顺序靠人排
  • 想关掉一个功能，要改这个文件
  • 前端在 public/index.html 手写全部 script 标签
现在 · plugins/pins/index.js一个插件
export const name = 'pins';
export const inject = ['launch', 'http', 'tmux'];

export async function apply(ctx) {
  const store = new PinStore(
    join(ctx.launch.configDir, 'pins.json'));
  await store.load();
  ctx.http.mount('/api/pins', createPinsRouter(store));
  ctx.provide('pins', store);
}
  • 自己声明依赖（inject），依赖就绪才启动
  • 注册的路由挂在自己的 ctx 上，插件停了就撤掉
  • 在 panel.yml 里列一行；关掉它只需一个补丁

1:从 dsh 借来的三个思想

DeepSeek Harness 能把很多功能做得互不牵扯，靠的是这三点。下面是每一点在本项目里落到了哪里。

没有特权内核

产品的每一部分都是插件

kernel/ 只有三个文件（profile、loader、app），约 350 行，只负责读配置、挂插件。HTTP 服务器、登录鉴权、tmux 本身也都是插件，和“置顶窗口”地位一样。

所以换掉任何一块都不用动内核：比如测试时把 tmux 插件配置成私有 server，整个面板就都跑在私有 tmux 上。

副作用可撤销

注册了什么，就能收回什么

插件经 ctx 注册的东西：路由、中间件、WebSocket 升级、定时器、事件监听、页面上的脚本，都记在这个插件名下。插件停掉，这些自动撤掉，不需要另写清理代码。

以前的关机流程是手工逐个 stop；现在是按依赖关系反向撤销。test/panel.test.js 验证了运行中关掉一个插件，它的接口立刻 404，再打开又恢复。

配置即组装

一份可打印、可覆盖的清单

整个产品就是 profiles/panel.yml 里那 42 行。不在清单里的插件不会被加载，代码里没有别的组装入口。

想改组装，不改清单，而是叠一层补丁（关掉、换实现、改配置、插入新插件）。node bin/panel.js --dump-config 打印叠完补丁后的最终结果。

2:目录地图

插件决定“什么时候、依赖谁、往哪里注册”，lib/ 决定“具体怎么做”。

profiles/panel.yml：整个产品的插件清单改组装用补丁，不直接改它新
bin/panel.js启动入口接受原来的全部命令行参数，加上 --profile、--patch、--dump-config新
kernel/读 profile 和补丁、挂载插件、运行时开关profile.js、loader.js、app.js新
plugins/<id>/每个功能一个目录：index.js 是服务端接线，client/ 是它的前端client/page.json 声明这个插件往主页面里放哪些脚本和样式新
lib/业务模块：路由、TerminalManager、会话保护、Hub 链路……来自原 server/，逻辑没改，只是由插件接线搬家
client/浏览器端的 Cordis 内核boot.js、核心服务 api、共享的 DOM 工具新
catalog/经过审核的面板插件（tmux-agent）原来在 plugins/tmux-agent，为了不和功能插件混在一起而改名搬家
vendor/Cordis、cosmokit、plugin-timer 的发布版，和 dsh 一样放进仓库还有原来的 tmux 子模块、tmux-resurrect新
server/index.js只剩一行 import给还指向旧路径的 systemd / launchd 服务单元用，启动的就是 bin/panel.js兼容

3:42 个插件和它们的依赖

按依赖分层：每一层只依赖它上面的层。点一个插件，看它做什么、依赖谁、谁依赖它。

它依赖的依赖它的

依赖靠插件里的 inject 声明。Cordis 等声明的服务都就绪了才启动这个插件；某个依赖被关掉，依赖它的插件跟着停，依赖恢复后再自动启动。清单里的顺序保持了原来 server/index.js 的顺序，但正确性不靠顺序。

4:一个插件的写法

以“系统监控”为例：服务端和前端放在同一个目录里。

plugins/metrics/
plugins/metrics/
├── index.js              服务端：挂 /api/system-stats 等路由
└── client/
    ├── page.json         往主页面放哪些样式和脚本
    ├── css/metrics.css   只有它的脚本产生的元素的样式
    └── js/
        ├── system-stats.js
        ├── perf-utils.js
        ├── perf-panel.js
        └── perf-section.js 注册服务器页的“性能”分区
// client/page.json
{
  "serve": ["."],
  "head": [{ "order": 50.5, "style": "/css/metrics.css" }],
  "body": [
    { "order": 230, "script": "/js/system-stats.js" },
    { "order": 240, "script": "/js/perf-utils.js" },
    { "order": 250, "script": "/js/perf-panel.js" },
    { "order": 255, "script": "/js/perf-section.js" }
  ]
}
要点
  • serve: ["."] 把 client/ 挂到网站根下，所以 /js/perf-panel.js 就是这个目录里的文件。
  • order 是全局顺序。各插件的脚本按它排进同一个页面；插件的样式表排在外壳的 style.css 之后（50.x），层叠顺序和合在一起时一样。
  • 外壳不认识这个插件：perf-section.js 往 PanelSlots.serverSections 里注册“性能”分区，插件关掉就没有这个分区。
  • 插件在 apply 里调用 ctx.ui.contribute(page.json)。这次登记也是可撤销的：插件关掉，脚本从页面上消失。
  • 服务端的业务逻辑在 lib/metrics/，插件只负责把它接到 HTTP 上。
  • 新功能照这个样子写成一个插件，再在 panel.yml 里加一行。

5:启动和关机

从服务管理器拉起进程，到第一个浏览器请求能被处理。

  1. 服务管理器启动 bin/panel.jssystemd、launchd 或 Windows 计划任务，环境变量（PORT、AUTH、TLS_*…）和以前一样注入。旧服务单元还写着 server/index.js 的，经那一行兼容入口转进来。
  2. 读清单 profiles/panel.yml得到 42 个条目，每条是 id、use（用哪个实现）、config、disabled。
  3. 叠补丁先叠配置目录里的 patch.yml（默认 ~/.config/tmux-web-panel/patch.yml），再叠命令行上的每个 --patch。没有补丁就是原样。
  4. Loader 挂载每个条目按清单顺序交给 Cordis；Cordis 按 inject 等依赖就绪再调用各插件的 apply。某个插件启动失败只影响它和依赖它的插件，进程最后以失败码退出，让服务管理器看得到。
  5. http 开始监听，ui 组装主页面此时所有路由、WebSocket 升级、页面脚本都已登记。
  6. 关机：反向撤销收到停止信号后按依赖反向撤销所有插件，比如先结束 Mosh 会话，再结束 Hub 的 Mosh 终端，最后断开到各 Node 的链路。最多等 15 秒。

6:一个 HTTP 请求怎么走

各插件注册的中间件和路由，由 http 插件按固定规则排成一条管线，不再取决于谁先 app.use。

order −100诊断计时diagnostics
→
order −50/n/:serverId 转发hub-relay
发往别的机器的请求在这里转给对应 Node
→
固定压缩http
→
order ≥ 0/api 守卫auth
没登录就 401
→
路由接口各功能插件
精确路径优先，其次按登记顺序
→
order 1000静态文件ui
各插件的 client/
→
最后404 / 错误http
WebSocket 走另一条路：升级请求先经 /n/ 转发和 auth 的令牌校验，再交给登记了该路径的插件（terminal 的 /ws/terminal/:paneId、status 的 /ws/status）。所有插件共用一个 WebSocketServer。

7:主页面怎么组装

以前 public/index.html 手写所有标签。现在 ui 插件收集各插件的 page.json，把脚本和样式按 order 填进模板。

terminal/client/page.jsonxterm、字体切片、终端脚本
files/client/page.json文件预览、分窗、files.css
metrics/client/page.jsonmetrics.css 和 system-stats.js 等 4 个脚本
… 另外 13 个插件keypad、git、notifications、agent-hub…
→
ui 插件按 order 排序，填进模板的 <!--ui:head--> 和 <!--ui:body-->
→
GET /本地 JS/CSS/字体的地址带上内容哈希 ?h=…，可缓存一年；HTML 本身每次校验。改前端文件刷新即生效，不用重启。
关掉一个插件时，页面和接口会发生什么？

浏览器这边也装了同一个 Cordis 内核（/client/boot.js，核心服务 api）。不过现有的前端脚本内部仍然是原来经全局对象互相调用的写法，还没逐个改成 ES 模块，这是后续可以慢慢做的事。

8:用补丁改组装

补丁是一个操作列表，按顺序作用在清单上。不需要改仓库里的任何文件。

# ~/.config/tmux-web-panel/patch.yml

# 这台机器不需要 Agent 控制台
- id: agent-hub
  disabled: true

# 测试：整个面板用私有 tmux server
- id: tmux
  config:
    socket: twp-test

# 加一个自己写的插件，放在 files 后面
- insert:
    id: my-tool
    use: ./my-tool/index.js
  after: files
{ id, disabled }关掉或重新打开一个插件
{ id, config }替换它的整份配置
{ id, use }保留 id，换一个实现
{ insert, after | before }插入一个新条目，默认放在最后
--dump-config打印叠完补丁的最终清单，不启动
--patch my.yml临时再叠一层，适合冒烟测试

9:没有变的

这次是换组装方式，不是重写业务。

业务逻辑

原 server/ 的模块整体搬进 lib/，逻辑不变。Windows 上 tmux 客户端那批契约（一次只换一个客户端、输入暂存、控制台回收）都还在 TerminalManager 里。

页面外观和行为

组装出来的主页面与原来手写的 index.html 一致，前端脚本没有改写。

启动参数

环境变量（PORT、HOST、AUTH、NODE_ONLY、TLS_*、HTTP_PORT、TMUX_PANEL_CONFIG_DIR）和命令行参数照旧。

数据和配置

配置目录还是 ~/.config/tmux-web-panel，令牌、通知、服务器列表、会话保护设置原地读取。

服务管理

仍然只经 systemd、launchd 或 install-service.ps1 启停。安装脚本已改成直接启动 bin/panel.js。

Hub 与 Node

/n/:serverId 转发、node token、证书指纹固定、直连和 Mosh 的规则都没变，只是分别落在 node、hub-links、server-health、hub-relay、mosh、mosh-hub 等插件里。

验证

整机集成
真实启动整个清单：登录、/api 守卫、WebSocket 鉴权、终端接入、运行时开关插件、页面和 /api/node/info 里的插件清单 通过
真实浏览器

样式拆分
拆出去的 8 个样式表合起来与原来的规则逐条相同；上面每个页面里每个元素的计算样式（含伪元素）与原来一个 style.css 时完全一致 0 差异

切换一台机器

  1. 拉取代码后运行 npm install（新增了 vendor/ 下的本地依赖）
  2. Linux、macOS 重新运行 scripts/install-service.sh install，服务单元改为直接启动 bin/panel.js。不重装也能启动：旧单元经 server/index.js 兼容入口进来。Windows 的计划任务经 run-panel.ps1 启动，脚本已经改好，不用重装
  3. 经服务管理器重启面板：systemctl --user restart tmux-web-panel，Windows 用 scripts/install-service.ps1 restart。浏览器里的终端会断开重连，tmux 会话不受影响

旧结构留下的两处路径由面板启动时自动修好：指向旧位置的 tmux-agent 技能链接，和 public/js/ 下的中继配置。

还可以继续做的

  1. 把前端的全局脚本逐个改成浏览器端的 ES 模块插件，全局对象换成服务
  2. 把右侧分窗从文件预览移进外壳，让 Git、浏览器 block 在没有 files 时也能停靠
  3. 把 lib/ 里的大模块（terminal.js、api/files.js、api/agent-hub.js）按接缝拆成更小的插件

都不影响现在的功能，可以随功能迭代逐步做。约定和陷阱写在 docs/plugins.md。
