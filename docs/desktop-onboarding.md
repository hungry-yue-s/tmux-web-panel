# 桌面客户端首次使用与验收

这份指南面向直接下载安装包的用户。源码部署、命令行安装器和 tmux 插件开发属于另一条路径，不是使用桌面客户端的前置条件。

## 下载前，先确认是哪一种安装包

从项目 GitHub 的 **Releases → Assets** 下载桌面安装包，不要把 **Source code (zip)** 当成 App。Apple Silicon 对应 `arm64`，Intel 对应 `x64`，在 macOS 的“关于本机”中可以查看芯片类型。当前完整包的最低系统要求为 macOS 13.5；只下载该次 Release 实际提供的附件。

当前本地构建为开发预览包，使用 ad-hoc 签名，没有 Developer ID 签名或 Apple 公证。最低版本元数据与依赖扫描不代表已经在 macOS 13.5 真机验收；Apple Silicon 上的 Rosetta `x64` 运行检查也不等于 Intel 真机验证。实际测试范围与签名状态以该次 Release 说明为准。

完整安装包包含服务端、Node 运行时、与其 ABI 匹配的 `node-pty`、项目维护的 tmux 及所需运行资源。用户不需要安装 Homebrew、Xcode、Node、npm，也不需要在第一次打开时编译 tmux。仅供开发调试的薄壳包不包含这些后台组件。

把 App 移到“应用程序”后再进行初始化，避免从临时解压目录或只读磁盘映像中长期运行。遇到系统提示时，按该次 Release 的签名说明核对来源；不要关闭 Gatekeeper 或复制不明来源的解锁命令。系统拦截的含义与处理入口见 [Apple 的应用安全说明](https://support.apple.com/102445)。

## 先完成本机使用

先填写本机工作台账号密码，再开始初始化。托管模式会检查内置组件和端口、安装托管运行时、生成登录与 HTTPS 凭据、注册用户级后台服务、检查连接，最后进入工作台。界面分别显示步骤结果；失败后先看提示与日志，再重试。

建议先选择“仅在这台电脑使用”。域名、手机连接、GitHub Pages、证书信任和双因素认证都不应阻塞本机初始化。离线时也应可以完成这条路径。

托管模式默认使用 `127.0.0.1:17681`，仅这台电脑能访问；它与源码安装常用的 `7681` 端口分开。检测到既有 LaunchAgent 安装时，默认沿用原服务，不自动覆盖或迁移。不要为了跟随本指南而改变一个已经工作正常的环境。

### 设置和运行状态放在哪里

从客户端的“设置与运行状态”进入初始化、服务状态、日志和可选网络设置。托管模式以 `~/Library/Application Support/Tmux Panel/settings.json` 作为统一设置入口，包含服务、身份哈希、访问范围和引导页配置，文件权限为仅当前用户可读写。不要手工把密码填进该文件，也不要把它发给他人。

同一个目录下的 `runtime/` 放置内置运行时的安装版本，`logs/` 保存诊断日志，`tls/` 保存证书材料，`relay-site/` 保存导出的引导网站。托管服务的标签为 `com.tmux-web-panel.desktop` 和 `com.tmux-web-panel.desktop.tmux`，使用自己的 tmux socket 与配置；不会把用户的 `~/.tmux.conf` 当成初始化目标。

修改账号、密码、端口、访问范围或引导入口后，先点击“保存设置”，再点击“应用并重启面板”。保存只更新配置，应用后后台服务才使用新值；现有 tmux 会话保持运行。开启局域网、更新 DNS、导出引导站点或生成手机二维码前，也要先完成应用。

更改账号或密码并应用后，当前客户端、浏览器和其他设备都需要重新登录；密码字段留空会保留当前密码。忘记密码时可在本机客户端的基础设置中重新设置，随后保存并应用，不要通过删除整个数据目录来重置。

如果检测到已有面板或运行中的 tmux，应先说明它们来自哪里，提供继续使用现有环境的选择。端口被其他程序占用时，不应自动结束那个程序。修复环境不等于重置环境；关闭客户端窗口也不等于停止后台任务。

完成后先做三件事：新建一个会话、运行一个简单命令、关闭窗口后重新打开并找到这个会话。电脑重启是另一种情况：tmux 的内存不会跨重启保留，窗口结构恢复需要另外配置会话保存与恢复，运行中程序的内存状态不会恢复。见[服务与会话持久化](service-install.md)。

### 更新和修复内置组件

替换 App 后，已经安装的后台运行时不会被自动覆盖。在“设置与运行状态”中点击“更新/修复内置组件”，可以把当前 App 自带的组件安装到一个新目录，并重启面板连接；操作不会停止 tmux 或删除旧运行时和个人数据。

只有能确认新旧会话引擎兼容时，才会继续更新。遇到“会话引擎需要迁移”时，保留当前版本和任务，单独安排迁移；不要通过停止 tmux 绕过检查。新组件连接检查失败时，程序恢复原配置并尝试恢复原面板，界面会说明恢复结果，原运行时仍保留。此功能使用当前 App 内置的组件，不会替你在线下载另一个版本。

## 什么时候需要选配远程访问

| 你的目标 | 需要什么 | 暂时不需要什么 |
|---|---|---|
| 只在这台电脑上使用 | 本机服务与工作台 | DNS、GitHub 账号、引导网页、手机证书 |
| 同一个局域网里的手机访问 | 开放局域网访问、登录保护、可达的电脑地址；使用 HTTPS 时还需信任对应证书 | 固定入口不是必需，先用当前地址验证 |
| 局域网地址经常变化，想收藏同一个入口 | 动态 DNS 记录与引导网页 | 不需要把工作台和终端数据上传到 GitHub Pages |
| 不同地点、不同网络访问 | 首先要有能到达电脑的网络路径 | 单独配置 DNS 或引导网页不会建立这条网络路径 |

**DNS 与引导网页不是内网穿透。** 引导页帮助手机找到电脑当前的地址；电脑仍需开机，手机仍需能够通过局域网或既有的网络路径到达它。同名 Wi-Fi 的访客隔离、电脑睡眠、VPN 路由变化、企业网络限制和系统防火墙，都可能阻止连接。应先验证当前 IP 能访问，再配置固定入口。

引导网页是一个公开的静态页面；它不托管服务端，也不运行 tmux。该方案会把选择的地址写入公开 DNS，客户端会在本地记住配置的入口。不要把账号密码、Duck DNS token、证书私钥、CA 私钥或会话 token 上传到 Pages 仓库。

### 第一步：创建你自己的动态 DNS 名称

1. 打开 [Duck DNS](https://www.duckdns.org/)，使用自己的账号登录。
2. 添加一个未被占用的子域名，例如 `my-workbench`。
3. 把子域名和账号 token 填回客户端“设置与运行状态”中的可选网络设置。子域名字段只填 `my-workbench`，不包含 `https://`、`.duckdns.org` 或端口。
4. 启用稳定入口后保存远程访问设置，再到运行状态应用并重启面板，最后点击“更新 DNS 地址”。区分“凭据已保存”“更新请求被接受”和“解析结果已正确”，不要把三者当作同一个状态。先确认当前局域网地址可访问，再做这一步。

Duck DNS 的更新协议及返回值可查阅[官方 API 说明](https://www.duckdns.org/spec.jsp)。保存 token 不应自动发布未经说明的地址；网络更新失败也不应影响已经可用的本机工作台。

客户端当前提供显式的“更新 DNS 地址”操作。电脑更换网络或局域网 IP 变化后，应重新更新并验证解析结果；仅保存设置不表示已经启用了持续自动更新。沿用旧安装的用户若使用原来的网络同步脚本，其生命周期仍由原安装管理，不应把两套配置混用。

### 第二步：发布你自己的引导网页

1. 登录自己的 GitHub 账号，创建专门用于引导页的仓库。若使用 GitHub Free，应选择可使用 Pages 的公开仓库；它不应存放任何私密材料。
2. 回到客户端，先填入计划使用的 Pages 地址，例如 `https://用户名.github.io/仓库名/`，并填好自己的 DuckDNS 子域名。保存远程访问设置并应用后，再导出引导网站文件，打开 `relay-site/` 查看生成内容。由你在自己的 GitHub 账号下上传导出目录中的文件；客户端不会替你创建或发布个人仓库。不要直接上传项目源码或其他人的已生成站点。页面中的域名与端口必须属于自己的部署。
3. 在仓库 **Settings → Pages → Build and deployment** 中选择 **Deploy from a branch**，再选择含站点文件的分支与 **/(root)**，保存。分支必须已经存在。
4. 等 GitHub 显示已发布的站点地址，核对它与客户端保存的地址一致；如有不同，修正客户端设置并重新应用。不要把 `github.com` 的仓库页面地址当成引导页地址。
5. 在手机上打开一次该地址，确认能找到自己的工作台，再把它加入收藏或用于客户端注册。

Pages 的发布路径、权限和账号限制以 [GitHub 官方说明](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site)为准。首次发布与更新有构建和缓存等待时间；“已导出文件”“已上传仓库”“站点已可访问”必须分别判断。

有 Git/`gh` 经验的用户仍可使用[命令行远程访问指南](roaming-access.md)，但它们不应成为首次本机初始化的要求。

### 第三步：在手机上验证

先检查手机与电脑的网络可达性，再处理登录或证书问题。证书名称不匹配、证书未受信任、登录凭据错误和地址解析失败是不同问题，不应一律提示“网络错误”。

只信任自己这台电脑生成并导出的 CA，不要安装来源不明的证书。普通叶证书续期保留原 CA；原 CA 缺失、损坏或不匹配时，客户端会报错，不会静默换成另一个 CA。先检查系统时间并从自己的备份恢复；更换 CA 需要在其他设备重新信任。

## 遇到问题时先看什么

| 现象 | 用户需要看到的原因和下一步 |
|---|---|
| 刚打开就是空白或一直“连接中” | 当前连接地址、后台服务是否存在、最近的启动错误，以及重试和日志入口 |
| 初始化失败 | 失败的是组件检查、写入目录、服务注册还是连接验证；已经完成的步骤保留，不要求从头重做 |
| 端口被占用 | 占用的端口与可选地址；不把另一个程序直接结束 |
| 内置组件缺失或架构不匹配 | 说明安装包不完整或下载的架构不匹配，回到 Releases 选择正确安装包 |
| 后台服务启动后立即退出 | 实际退出状态与错误日志，不把“已注册”显示为“运行正常” |
| 终端提示找不到 node、tmux 或动态库 | 显示组件路径和版本；完整包应由内置组件运行，不能依赖开发者电脑上的 Homebrew 路径 |
| 已有环境不能用 | 显示采用的是既有安装还是客户端托管安装；保留原配置与现有任务，避免自动覆盖修复 |
| 手机无法连接 | 分开检查电脑是否开机、当前地址、局域网访问开关、路由/防火墙、HTTPS 信任、账号登录 |
| 引导页仍显示旧地址或 404 | 区分 DNS 更新、Pages 构建与浏览器缓存；当前 IP 直连仍可作为排障入口 |
| 电脑重启后没有原来的会话 | 解释 tmux 会话保存的实际范围；没有配置恢复时不要承诺重启后继续运行原进程 |
| 更新后异常 | 显示当前 App 与运行时版本，保留可恢复配置；回退不应抹掉工作区数据 |
| 修复提示会话引擎需要迁移 | 当前引擎与新 App 不兼容或无法确认兼容；保持任务运行，保留当前版本并另行安排迁移 |
| 修改账号或密码后设备提示登录失效 | 应用设置后旧登录失效，使用新的账号密码重新登录 |
| 想卸载 | 区分关闭窗口、退出客户端、停用后台服务和删除个人数据；停止 tmux 前说明运行任务会被结束 |

日志中不应记录明文密码、token、私钥或完整登录交接 URL。向他人发送诊断信息前，先确认其中不含个人路径和敏感信息。

## 维护者发布验收清单

下面是发布门槛，不代表每一个历史安装包都已经通过。Release 应写清实际验证过的系统、架构和结果。

- [ ] 在没有 Node、npm、Homebrew 和 Xcode 的干净账号/系统中安装；只靠 App 自带的组件完成本机初始化。
- [ ] 关闭互联网连接后，本机首次初始化和终端仍可使用；DNS/Pages 不会阻塞必选步骤。
- [ ] 用包含空格、中文和特殊字符的用户名/安装路径运行；运行时、动态库、配置和日志路径均正确。
- [ ] 端口占用、只读目录、磁盘空间不足、组件缺失、错误架构均有明确提示，重试不会重复创建服务。
- [ ] 已有手工部署和已运行的 tmux 会话不会被覆盖、重启、改配置或删除。
- [ ] 首次引导明确展示当前访问范围、配置保存位置以及下一步会执行的动作。
- [ ] 服务监控区分“组件存在”“服务已注册”“进程运行”“接口健康”“工作台可访问”。
- [ ] 拒绝通知、相机或文件访问权限后，其余功能仍可使用，之后能找到重新授权入口。
- [ ] 完成初始化后退出并重开 App、注销并重新登录；验证服务行为与界面说明一致。
- [ ] 对有活动会话的环境执行更新/回退；保留配置与数据，不把杀掉 tmux 当作修复方法。
- [ ] 使用自己的 Duck DNS 与 Pages 账号完成选配流程；验证域名格式错误、token 错误、未发布分支和离线情况。
- [ ] 使用手机分别验证当前 IP 与引导入口，确认网络不通、证书不受信任和登录失败分别呈现。
- [ ] 每个分发架构独立验证 Node 版本、`node-pty` ABI、tmux 版本、动态库依赖与签名；不把单台开发机运行成功当作全平台验收。
- [ ] 下载站点提供版本、架构、最低系统版本、校验值和实际签名/公证状态；不指导用户关闭系统安全检查。
